# Original/audio path compatibility

The exact `79e506ace65a99352b1bdd9af35b9df7f541b260` Windows job failed eight audio/controller assertions before packaging: [job 117788810493](https://github.com/Onyx-Dev-Labs/doodle-note/actions/runs/39165951862/job/117788810493). Those failures remain part of the original evidence.

The manifest binds `realpathSync(meetingsDir)`. The audio adapter used `fs.promises.realpath`, which has native realpath semantics. Those APIs can return different path strings for the same filesystem object: an actual macOS case-alias fixture reproduced a manifest path ending in `meetings` while the promise returned the created spelling `Meetings`. The adapter rejected valid audio because the hashes differed. Windows short temporary paths are a corresponding compatibility risk; the hosted Windows rerun is required to verify that platform, rather than inferring a Windows pass from macOS.

The desired-behavior regression uses real filesystem paths and actual retrieval/manifest/audio adapters. On a case-insensitive filesystem it accesses a created `Meetings` directory through `meetings`; on a case-sensitive filesystem it exercises the same valid directory without skipping or mocking canonicalization.
