# Smallest next reliability investigation

This is a proposed follow-up investigation, not a production change or a waived gate. Keep the current strict parser, original evidence policy, frozen corpus and output limits unchanged while completing the recorded run. Do not repair trailing text, reclassify failed cases or replace them with successful retries.

The first 13 native cases at `79e506a` already establish two distinct failures: seven native responses append a double quote after an otherwise complete JSON object; two parseable responses choose `conflicting-evidence` but emit only `quotation` claims. The engine returns native `responseText` directly, and the observer forwards the same prompt/options/result. Four other cases complete and validate. The retained raw outputs distinguish a format/schema failure from a tokenizer, retrieval or harness substitution problem. The must-find slice independently exposes the same trailing-quote failure, responses exceeding the existing 12-claim cap, and conflict claims with only one evidence ID. These are separate strict-validation failures even when the required gold passage was on the wire; final counts are recorded in the native results.

The smallest experiment is a separate, explicitly labeled diagnostic variant of the local cited adapter that constrains decoding to its existing JSON shape using the already installed node-llama-cpp 3.20.0 grammar API. Keep the question, evidence, model artifact, temperature, token/context/output budget and strict downstream validation fixed. Start with a tiny recorded-failure/control set; retain OLD and experimental attempts without replacing the original evaluation. Measure parse/schema validity, model/grammar setup time, output tokens and cleanup on abort/output limit. Do not run or ship this experiment as part of the unchanged79 evidence.

The [official grammar guide](https://node-llama-cpp.withcat.ai/guide/grammar#json-schema) documents `llama.createGrammarForJsonSchema(...)` and passing grammar to the chat call. The cached 3.20.0 types confirm the API, object properties, enum/oneOf and array limits. Do not assume full JSON Schema support: its string type exposes length constraints but no arbitrary pattern, and required properties are all declared properties. First prove a complete JSON root and existing enum/array shape; use the existing validator for uniqueness, exact supplied evidence membership, claim ID rules and status/conflict relationships. If needed, investigate an explicit prompt contract for the already required conflict relationship as a separate change, not parser relaxation.

A grammar can constrain syntax, not truth. Even a successful format experiment would still require all frozen semantic cases, designated independent human support/contradiction scoring, adversarial containment, performance review and fresh independent code review before rollout. The known 1k relative latency failure and repeated full-manifest cost remain independent gates.
