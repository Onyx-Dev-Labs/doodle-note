### Separate raw WAV runtime qualification

The review's actual host afconvert output uses WAVE_FORMAT_EXTENSIBLE (65534). Host Python 3.9.6 rejects that raw header. The review normalized headers without changing samples solely to test tone tolerance; that result is **not** an end-to-end raw-pipeline pass or a new F2 regression. This patch neither normalizes output nor changes the reader/workflow.

The workflow invokes unpinned `python3` for tests and the verifier, with no setup-python step. Its in-process `wave` reader uses that interpreter; the restricted PATH in `runtime_env()` applies only to candidate subprocesses. The [official macOS14 ARM64 image inventory](https://raw.githubusercontent.com/actions/runner-images/main/images/macos/macos-14-arm64-Readme.md), inspected October 20, 2026, lists image `20260831.0302.1`, OS14.8.9 and Python3 3.14.7. [Python documents PCM WAVE_FORMAT_EXTENSIBLE support beginning with 3.12](https://docs.python.org/3.12/library/wave.html). Thus the documented runner default supports this format, but the unpinned workflow has not recorded its actual interpreter or passed the raw candidate pipeline. Local 3.9 unit/syntax success does not qualify raw extensible WAV decoding. No newer local interpreter was available on PATH; none was installed.

This avoids new interpreter downloads or dependency changes on the documented capable runner; explicit interpreter pinning can be considered only if its actual runtime differs.
